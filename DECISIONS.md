# Decisions

Working list for deciding features, approach and technical details. This file overrules `ARCHITECTURE.md` and `ROADMAP.md` wherever they disagree.

Each item has a code: the letter is the `ROADMAP.md` phase, the number is its sequence within that phase. Codes are stable and never reused. A new feature takes the next unused letter.

Status:
- **Decided**: settled and binding. State the choice and the reason in a few words.
- **Inspect**: needs a look first (spike, library, benchmark, test). Research only.
- **TBD**: read, but not discussed yet. Ask, don't guess.
- **Question**: raised (usually by the agent) and not yet read by the human. Triage it by moving it to TBD, Inspect or Decided. Treat it like TBD until then.

A phase starts only when its rows are Decided.

| D4 | Profile edits | Decided | Claude records facts via hidden tags: `<person id="P2">` for people in the prompt (handles P1, P2, ... map to LIDs), or `<person name="…">` for anyone else, from any chat. A name resolves to the best-matching known person (exact name, contains, or a word of a display name), and an unknown name gets a name-only profile (`name:<name>`). When two known people share a name, labels add an ID tag (last 4 digits of the LID or number, or `name` for name-only), e.g. `Omar #9249`, which Claude can use to pick one (user request). Anyone can trigger fact saving (changed from "only people in the prompt" by the user: "save facts about anyone, it's a knowledge system"). Only a whitelisted requester can make it forget or correct a fact. Strangers in DMs get no profile (B7). User choice. |

(The per-person fact cap was replaced by D7.) Accepted by the user as proposed. |
| D7 | Fact retrieval | Decided | Person facts have no cap. With API-style providers, the model gets a `search_facts` tool (full-text search) that covers every known person, from any chat, by handle, by name or by fact text; changed from "scoped to people in the current prompt" by the user. Trade-off accepted: anyone who can trigger the bot can ask what it knows about people from other chats. The prompt shows only fact counts for people present. A search with no match on a named person returns their newest facts. In CLI mode (no custom tools) all facts of people present go inline, trimmed by the 128k cap (B17). User request. |

CLI mode enables only Claude Code's WebSearch/WebFetch. Web content is treated as data. Switch: `WEB_TOOLS`. User request. |

| H1 | Knowledge curator | Decided | The people knowledge updates itself: a background pass reads new messages in every chat the bot sees (groups it is in, whitelisted DMs), including ones not addressed to it, and saves new facts with the same tags (D4). A pass runs per 16 unread messages in a chat, or after 10 minutes of quiet if any are unread; messages are taken before the 16-message window prunes them. Passes run one at a time, without web tools, on the configured provider (about $0.001 per pass on DeepSeek). Group members are not told (B11). User choice. |
| H2 | What the curator records | Decided | Durable facts about participants and people they mention: identity, relations, studies/job, origin, interests, habits, opinions, plans, running jokes, how they treat the bot; compressed English facts, no duplicates of known facts. Never sensitive data (passwords, phone numbers, addresses, health, money). Agent's proposal, accepted with H1. |
| H3 | Nicknames and merging | Decided | The curator records nicknames as `Alias: <name>` facts (e.g. "Wayan itu aku"), and name lookups also match aliases. When an alias matches a name-only profile (D4), that profile's facts move to the real person and the name-only profile is deleted. User choice. |
| I1 | API tools | Decided | Two kinds of client-side tools, run by the bot in the same tool loop as `search_facts` on every provider: a generic `http_request` (any method, headers, body; `find` to grep big responses like API docs, `offset` to page; 20k characters per result), and the tools of configured MCP servers, named `mcp__<server>__<tool>`. The model is told to look for an app's API docs instead of guessing endpoints, and to call an app's API when its web page needs JavaScript. If tool rounds (8) run out, one final call without tools forces an answer, and leaked tool-call markup is stripped. Switch: `API_TOOLS`. User request ("API MCP, all-purpose"). |
| I2 | Who may use API tools | Decided | `http_request`: anyone who can trigger the bot. MCP tools: only whitelisted requesters. `http_request` can only reach public addresses: loopback, private, link-local (cloud metadata), CGNAT and multicast IPs are refused at connect time, also after redirects and DNS tricks, and proxies are off. Trade-off accepted: group members can make the VPS send requests to public sites. Tool results are data; the model must not repeat secrets from them. User choice. |
| I3 | MCP configuration | Decided | Only the owner configures MCP servers (and only whitelisted requesters can use them, I2), in `mcp.json` (Claude Desktop format: `command`/`args`/`env` for stdio, `url`/`headers` for streamable HTTP) at `MCP_CONFIG` (default `DATA_DIR/mcp.json`, secret like the rest of `data/`). Servers connect at startup (restart after editing); a failing server is logged and skipped; a dead session reconnects once. Uses the official MCP Go SDK (new dependency, approved). User choice. |
| I4 | Stored API keys | Decided | Chosen by the user (2026-11-06) over an MCP server for one app. Owners keep API credentials on the VPS in `DATA_DIR/api_keys.json` (secret like the rest of `data/`, chmod 600), a map of host to request headers, e.g. `{"tasks.example.com": {"Authorization": "Bearer <token>"}}`. `http_request` adds them only for whitelisted requesters and only on https requests to that exact host; a redirect that leaves the host or https drops them. The model never sees a key: the tool description lists only the hosts, and any key echoed in a response or error is replaced with `[stored credential]`. Read at startup (restart after editing); no new `.env` key. Accepted risk, as with MCP tools (I2): an owner's request can make the model use the key for any method on that host, including writes. |
| J1 | Fact validity (bi-temporal facts) | Decided | Raised by the user (from Rin's review): every fact is true forever. Proposed: each fact gets `valid_from`, `invalid_at`, `invalid_reason`, `said_by` (person key), `chat`, `tier` (J4) and `kind` (`fact`, `state` for short-lived things like "on the way home", `claim`/`joke` for unverified talk). Outdated or contradicted facts are invalidated, not deleted, and kept as history; search returns only valid facts unless history is asked for. `state` facts expire on their own (e.g. after 24 h). Forget (D4) becomes invalidate. Existing facts migrate with `valid_from` = when saved, tier `legacy`; `Claim:`/`Joke:` labels map to `kind`. Graphiti/Zep's bi-temporal edges are the reference; we copy the idea, not the framework. Existing facts migrate and are reclassified: `Claim:`/`Joke:`/`Behavior:` labels map to `kind` and tier `legacy`, so they rank low and show as unverified; nothing is deleted. User choice. |
| J2 | Hybrid retrieval | Decided | Raised by the user: FTS5 keyword search misses paraphrase ("how's his job going" vs "Job: IoT engineer"). Proposed: keep BM25, add embedding vectors, fuse with reciprocal rank fusion (RRF). Must keep `CGO_ENABLED=0` (C4), so no sqlite-vec. To inspect, with evidence (binary size, RAM on the 1 GB VPS, latency, recall on the J6 golden set): (a) a pure-Go embedding model shipped in the binary, (b) an embeddings API (provider, cost, new key), with vectors as SQLite BLOBs and brute-force cosine, which is enough below ~100k facts. Don't choose until measured. Approved for research by the user; bring measurements and options, then the user chooses. **Findings (2026-11-05)**, 24 paraphrased questions (English and Indonesian) against the 60 live facts, recall in the top 10: (a) today's FTS5/BM25 global search 14/24; most misses are "what does <name> ..." questions, because a name in the query returns that person's newest facts instead of the relevant ones. (b) Same FTS, but scoped to the named person and ranked by the rest of the query (code-only fix): 17/24. (c) Embeddings via OpenRouter (`openai/text-embedding-3-small`, 512 dims, same API key, no new dependency): 23/24 (20/24 in the top 5). (d) RRF of FTS and embeddings: 20/24, worse than embeddings alone here because FTS adds noise. Cost of (c): about $0.02 per million tokens, so embedding 10k facts once is under $0.01; each search adds about 0.85 s (median single-query latency) and one API call; 2 KB per fact (10k facts = 20 MB, brute-force cosine in a few ms). Free embedding models were not used: free endpoints may log or train on inputs. (e) A pure-Go model in the binary was not measured: it needs a new dependency and 90-500 MB of weights (binary 25 MB to 115 MB or more, roughly 200-300 MB RAM on the 1 GB VPS); a spike needs approval to add the dependency. Caveat: the model writes its own search keywords, usually label words, so real recall sits between these raw-question numbers and 100%; and with a person given, a miss already falls back to their 30 newest facts. Options to choose from: (b) only; (b) + (c); (b) + (d); or a spike of (e). **Chosen: (b) + (c)** (user choice). FTS scoped to a named person, plus embedding search via OpenRouter (`EMBED_MODEL`, default `openai/text-embedding-3-small` at 512 dims; empty disables, and the Anthropic provider has none). Results are the union of the embedding hits close to the best one and the FTS hits, then ordered valid first, by tier (J4), then by relevance. The embedding call runs in parallel with FTS, query vectors are cached, and if embedding fails search falls back to FTS. Vectors are stored per fact and dropped when a fact is deleted or its text changes; a background loop embeds facts that have no vector. |
| J3 | Tool-based memory writes | Decided | Raised by the user: hidden tags fail silently and can leak. Proposed: replace `<person>`, `<forget>` and `<memory>` with tools: `save_fact(subject, content, kind)`, `invalidate_fact(id, reason)`, `save_memory(category, content)`; the bot validates input, attaches provenance (J1, J4) and returns errors to the model. The curator (H1) uses the same tools. `<persona>` stays a tag, or becomes `set_persona` (owner only). CLI mode has no custom tools, so tags stay as its fallback. User choice. |
| J4 | Source tiers | Decided | Raised by the user: anyone can write facts about anyone, a poisoning surface. Proposed tiers, highest first: `owner` (a whitelisted person said it), `self` (the person about themselves), `participant` (someone else in the chat), `inferred` (curator's reading of the chat). Search ranks by tier and labels anything below `self` as unverified; a lower tier can't invalidate a higher one; claims about another person's identity ("X and Y are the same person") are always `claim`. Existing D4 rights stay (anyone can add); the tier decides weight. User choice. |
| J5 | Token accounting | Decided | Raised by the user: 1 token per 3 bytes is a guess, and the trim order can evict the memories a request needed. Proposed: per-section budgets (system + persona, people, memories, summary J8, history, request), with the request and its directly relevant memories protected, and history trimmed first. To inspect: a real count per model (Anthropic `count_tokens` is exact but adds a call; OpenRouter only reports usage after the fact) versus a calibrated estimate from logged `usage`, comparing cost and latency. Approved for research by the user; bring measurements and options, then the user chooses. **Findings (2026-11-05)**, real prompts rebuilt from the live data (system prompt 5.5 KB, chat prompts 4-6 KB), tokens counted by DeepSeek via OpenRouter usage and by Anthropic `count_tokens`: the estimate (bytes/3) vs real is 0.95-1.49 for DeepSeek (usually an overestimate, safe) and 0.61-1.03 for Claude (an underestimate by up to 40% on Indonesian and mixed chat, about 1.8 bytes per token). Real prompts are about 3-5k tokens in total against the 128k budget, so trimming never fires in normal use, only with giant pastes. The risk is a near-budget prompt on Claude: estimated 128k could really be about 210k, over the 200k window, giving an API error instead of a trim. Options: (a) a safer constant, bytes/2: free, no latency, over-trims DeepSeek. (b) Calibrate per model from the `usage.prompt_tokens` every reply returns (a running ratio, stored): free and accurate after a few replies. (c) Exact counts with Anthropic `count_tokens`: free, but adds a median 574 ms (max about 1 s) per reply, and Anthropic only, since OpenRouter has no count endpoint. (d) A local tokenizer per model: a new dependency and vocabulary files. Per-section budgets: with prompts at 3-5% of the budget, the evidence favours simple caps over a budget system: cap each history line (e.g. 2,000 characters) and the request (e.g. 16k characters) so one paste can't evict memories, and protect the request plus the top 3 memories from trimming. The trim order otherwise stays history, then memories, then summary, then people. **Chosen: (b) + caps** (user choice). The bytes-per-token ratio is learned per model from the first round's reported prompt tokens (a running average, stored, starting at 3, with a 10% safety margin), and tool definitions count in the fixed part. Caps: each history line at most 2,000 characters, the request at most 16,000; when trimming, the request and the top 3 memories go last (history, then memories beyond 3, then summary, then people other than the requester, then the last memories, then the request). |
| J6 | Eval harness | Decided | Raised by the user: changes are untested beyond unit tests. Proposed: a golden set run on a cheap model before every deploy: trigger vs no trigger, reply to an image, prompt injection, persona change by a non-owner, cross-chat "what do you know about X", invalidate/forget, contradiction handling, tier ranking, no tool markup or narration in replies. Each case has a checkable expectation; `deploy.sh` runs it and stops on failures, with a flag to skip. Budget per run to be agreed. User choice; budget $0.05 per run (agent's proposal, accepted). |
| J7 | Scheduler and reminders | Decided | Raised by the user: the bot can't act on its own ("remind you to eat"). Proposed: a `schedule_message(chat, at, text)` tool; jobs stored in SQLite, sent through the pacer (B18), surviving restarts. Who may schedule (whitelisted only?), per-chat limits, recurring jobs and cancelling are open. User choice; the open details are in J9. |
| J8 | Rolling chat summary | Decided | Raised by the user: the 16-message window (B5) loses the shape of long chats. Proposed: the curator pass (H1) also updates a per-chat rolling summary (capped at ~300 words), shown in the prompt before the transcript. User choice. |
| J9 | Scheduler details | Decided | Recurring jobs are allowed ("every day at 12"), and the model may schedule on its own initiative (e.g. a meal or sleep nag), not only on request. The rest is in J10. User choice. |
| J10 | Scheduler limits | Decided | Whitelisted requesters can schedule one-off or recurring messages in any chat they are in (by group name, or their own DM); others only one-off reminders for themselves in the current chat. Self-initiated jobs (the model's own idea, e.g. a meal nag) only in chats with a whitelisted member. At most 10 pending jobs per chat; recurring jobs run at most hourly (hourly, daily, weekdays, weekly). Jobs are listed and cancelled by asking ("what reminders do you have?", "cancel the lunch one"): people cancel their own, owners cancel any, including self-initiated ones. A one-off missed while the bot was down is sent late if under 12 h late, else dropped; a recurring one skips missed runs. User choice. |
| J11 | Repetitive facts overwrite | Decided | Raised by the user after one spammer piled up ~50 near-identical `Behavior:` facts. A new fact that nearly repeats a stored valid fact of the same person overwrites it in place, and the old copies are deleted, not kept as history. Near-duplicate: same label, at least 2 shared content words and at least half the content words of the shorter fact (stopwords, generic verbs like asks/says/calls, and short words ignored; plural s trimmed). `Alias:` facts are never merged. A less trusted source can't overwrite a more trusted fact (J4): the new one is dropped. No cap per label and no collapsing of repeated chat messages (options the user declined). User choice. |
| J12 | Merge profiles of the same person | Decided | Raised by the user: duplicate profiles (a name-only "Andi" next to the real "Andi Pratama"). (1) By LID/number: when a person's LID and number are both known, a `pn:<number>` profile from before the LID was known merges into the LID profile. Two LID profiles are never merged. (2) Guessed from chat: a `name:` profile merges into a real account when its name or a nickname matches (a word equal to, or the start of, a word of the other, at least 3 letters) and that account is in a chat the facts came from (a group member, or the other side of a DM); exactly one account must qualify. A `name:` profile with no facts merges on a single name match. The old name is kept as an `Alias:` fact. Runs at startup and after a curator pass that saved something. Merging moves facts with their tiers and history (J1, J4). User choice; matching rules are the agent's proposal. |
| K1 | Standing preferences in every prompt | Decided | Raised after the owner asked Rin to stop mentioning the time (2026-11-06 04:59) and she kept doing it. The rule was saved (owner fact + memory), but under D7 facts reach the prompt only when the model searches, and memories only when the request shares a word with them ("Dumass", the nickname pull nothing). Option: always put the requester's owner-tier `Prefers:`/`Rule:` facts (a few lines) into `<people>`, an exception to D7's counts-only rule. |
| K2 | Grounding rule for claims about the past | Decided | Rin invented "I called you <nickname>, you answered <nickname> back" (not in the transcript), then defended it when quoted back ("Yes. That's exactly what I said"). Replays (24 runs, 4 variants) did not reproduce that line but showed smaller invented past events ("I woke you at five", "I was here the whole night"). Option: a system-prompt rule: claim what someone (including you) said earlier only if it is in the transcript, summary or a tool result; when told you said something you didn't, re-read the transcript instead of defending it. Built with the "find the line where it happened" wording: A/B on the golden case gave 0/8 without a rule, 2/8 with a plain re-read rule, 4-5/8 with this one. |
| K3 | Stronger model for owner DMs | Decided | Rejected by the user (2026-11-06): keep one model.
