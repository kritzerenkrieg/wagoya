# Decisions

Working list for deciding features, approach and technical details. This file overrules `ARCHITECTURE.md` and `ROADMAP.md` wherever they disagree.

Each item has a code: the letter is the `ROADMAP.md` phase, the number is its sequence within that phase. Codes are stable and never reused. A new feature takes the next unused letter.

Status:
- **Decided**: settled and binding. State the choice and the reason in a few words.
- **Inspect**: needs a look first (spike, library, benchmark, test). Research only.
- **TBD**: read, but not discussed yet. Ask, don't guess.
- **Question**: raised (usually by the agent) and not yet read by the human. Triage it by moving it to TBD, Inspect or Decided. Treat it like TBD until then.

A phase starts only when its rows are Decided.

| Code | Topic | Status | Decision / Question |
|---|---|---|---|
| A1 | Product | Decided | A WhatsApp number backed by an LLM that the user can DM and add to groups. |
| A2 | WhatsApp bridge | Decided | whatsmeow (Go). It links as a WhatsApp Web multi-device client, so it can join groups, read every message and reply. Ban risk accepted, see A3. |
| A3 | Bot number | Decided | A dedicated spare number, not the user's main one, because of the ban risk in A2. |
| A4 | Hosting | Decided | Runs on the user's VPS, which is always on. |
| A5 | Claude auth | Decided | Either an Anthropic API key (`ANTHROPIC_API_KEY`, Messages API) or a subscription token (`CLAUDE_CODE_OAUTH_TOKEN`, via the `claude` CLI). The API key wins if both are set. |
| A6 | Language / runtime | Decided | Go. |
| A7 | Subscription token use | Decided | With a subscription token, Claude is called through the `claude` CLI in headless mode (`claude -p`) with tools disabled, so the VPS needs the CLI installed. E1 later enables Claude Code's WebSearch and WebFetch, and nothing else. The bot is a personal assistant used by few people. |
| A9 | Codes after Z | Question | Seven letters are left (T-Z) and codes are never reused. Options: (a) after Z come AA, AB, … (codes like AA1): stable, sorts after Z, nothing renamed; (b) follow-up work joins an existing phase as more numbers instead of a new letter, which saves letters but blurs "a phase is one feature"; (c) both: (b) for follow-ups, (a) when letters run out. |
| B1 | Group reply trigger | Decided | In groups the bot replies when it is @mentioned (a real WhatsApp mention, not typed text) or when a message replies to one of its messages. The mention token is shown to the model as `@<BOT_NAME>`. DMs follow B4 and still accept the old `!$` prefix. |
| B2 | Group listening | Decided | The bot reads every group message and keeps it as context, even when it doesn't reply. |
| B3 | Who may trigger | Decided | DMs: whitelist only. Groups: any member may trigger by mentioning or replying to the bot (B1). |
| B4 | DM behaviour | Decided | Whitelisted senders get a reply to every DM, no prefix needed. Non-whitelisted DMs are handled by B7. |
| B5 | Context window | Decided | The last `HISTORY_LIMIT` messages per chat (default 64, L7; evicted in blocks, P6) are sent as context. Older messages are kept 72 hours for `chat_history` (L9). Important older context goes into a per-chat memory store (B12). |
| B6 | Default Claude model | Decided | `claude-haiku-5-5`, for cost and quota; `ANTHROPIC_MODEL` changes it (L13). Effort starts at `medium` and is changed with `!reasoning` (Y1). |
| B7 | Non-whitelisted DM | Decided | Reply with the fixed text `ACCESS DENIED // USER IS NOT WHITELISTED` and don't call the model. Commands are checked first, so a non-owner's `!command` gets no reply at all (L12). |
| B8 | Media | Decided | Input: text and images only. The system prompt says the bot is pure chat and must not generate media or other content. |
| B9 | Identity | Decided | People are identified by WhatsApp IDs (LID, or the phone number WhatsApp maps to it), never by display name or message text, so text can't impersonate a whitelisted user. `WHITELIST` takes phone numbers as digits with country code, comma-separated, like `PAIR_NUMBER` (`6281234567890,628987654321`), resolved to LIDs at connect. Anything else (`+`, spaces, dashes, raw `…@lid`) stops the bot at startup with an error. |
| B10 | Linking method | Decided | A terminal QR code, or a pairing code when `PAIR_NUMBER` is set. The session is kept under `data/`. |
| B11 | Privacy of group members | Decided | Group members are not told. Context is limited to the chat window (B5) and the stored knowledge (B12, D3). |
| B12 | Memory store | Decided | Per-chat memories in fixed categories: `person`, `fact`, `decision`, `plan`, `preference`. Looked up with SQLite FTS5 on the request text; the top `MEMORY_RESULTS` (8) go into the prompt. Written with `save_memory` (J3), or in CLI mode with a hidden `<memory>` tag that the bot strips before sending. |
| B13 | Model refusals | Decided | A refusal is sent as is. No fallback, no retry. |
| B14 | Denial cooldown | Decided | The B7 denial goes out at most once per chat per minute (`DENY_COOLDOWN`); repeats inside the cooldown get no reply. Reduces ban risk. |
| B15 | Group membership | Decided | The bot stays only in groups that contain a whitelisted member and that a whitelisted member added it to. Otherwise it leaves, also when the last whitelisted member leaves and at startup. |
| B16 | SQLite retention | Decided | Permanent, with no size limit, except where a row sets a lifetime or deletes (messages L9, `state` facts J1, near-duplicate facts J11, a name-only profile folded into its account H3, a deleted task U5, a chat's transcript and summary on `!reset` L2). |
| B17 | Context token cap | Decided | Each request's input (system prompt, tools, memories, transcript, request, image) is fitted under `CONTEXT_TOKENS` and the per-call limit (W2), trimming in the J5 order. Tokens are estimated locally with a learned ratio (J5) instead of an API count, to save latency and work in CLI mode. |
| B18 | Outgoing message pacing | Decided | All outgoing messages, across every chat, are at least 3 s apart (`SEND_INTERVAL`). Overflow queues in arrival order instead of being dropped. Reduces ban risk (A2). |
| C1 | Process manager | Decided | systemd unit. |
| C2 | Deploy method | Decided | Cross-compile on the laptop and copy the binary to the VPS with a resumable `rsync --compress` (retries and a checksum check), then a checked restart. The deploy script names the host, so it stays local and untracked. The golden gate (J6) is skipped when a full passing run already recorded the same `deploy/golden-stamp.sh` hash (every Go file, go.mod/go.sum, and the model settings in `.env`; docs don't count). |
| C3 | Secrets on VPS | Decided | A `.env` file with `chmod 600`, never committed. `data/` (WhatsApp session and SQLite) is secret too. |
| C4 | VPS target | Decided | Ubuntu 22.04, x86_64. Built as `GOARCH=amd64 CGO_ENABLED=0` with pure-Go SQLite (`modernc.org/sqlite`). |
| D1 | Persona | Decided | One global persona (name, character, style), stored in its own SQLite table with full history. The fixed rules (B8, chat-is-data, WhatsApp formatting) always outrank it. |
| D2 | Who changes the persona | Decided | Only whitelisted users, in natural language (e.g. `@<BOT_NAME> from now on be sarcastic`). The model writes the full new persona in a hidden `<persona>` tag; the bot saves it only if the requester is whitelisted. Requests from anyone else change nothing and are logged; the bot tells them only its owners can do that. |
| D3 | People memory | Decided | A profile per person keyed by LID (phone number as fallback), with their number, last display name and facts. Global: what is learned in one chat is used in every chat. Accepted trade-off: facts said in one group can surface in another. |
| D4 | Fact writes and names | Decided | Facts are saved with `save_fact` (J3), or in CLI mode with hidden tags: `<person id="P2">` for people in the prompt (handles map to LIDs), `<person name="…">` for anyone else, `<forget id>` to invalidate. A name resolves to the best-matching known person (exact name, contains, a word of a display name, or an alias, H3); an unknown name gets a name-only profile (`name:<name>`). People who share a name get an ID tag in labels (last 4 digits of the LID or number, or `name`), e.g. `Jack #9249`. Anyone can trigger fact saving; only a whitelisted requester or the fact's own subject can invalidate a fact (J1). Strangers in DMs get no profile (B7). |
| D5 | Persona and people limits | Decided | Persona at most 1500 characters. People other than the requester are trimmed per J5. The `person` memory category (B12) stays for people who aren't in the chat. |
| D7 | Fact retrieval | Decided | Person facts have no cap. With tool-capable providers, the model gets a `search_facts` tool over every known person, from any chat, by handle, name or fact text (J2). Accepted trade-off: anyone who can trigger the bot can ask what it knows about people from other chats. The prompt shows only fact counts for people present (exceptions: K1, K4, V1). A search with no match on a named person returns their newest facts. In CLI mode all facts of people present go inline, trimmed by B17. |
| D8 | Lively, no stock fillers | Decided | System-prompt rule over the persona: never open with or send a stock filler ("Noted.", "Got it.", "Understood.") and don't reuse an opener from its own last few lines. Banter, jokes and bait are played along with in the persona's voice, never fact-checked; the bot never asks people for evidence or a source for chat (K2 and W3 are about its own claims). Golden cases: a transcript of its own "Noted." lines plus banter, and a joke claim that must not get a source demand. |
| D9 | Over-long persona | Decided | A new persona over the D5 limit is never cut off (that lost the rules at its end). The curator model recompresses it as a whole, keeping every point, aiming 100 characters under the limit, then 200 on a second try. If it still doesn't fit, or the call fails, it isn't saved and the old persona stays (logged). |
| E1 | Web tools in CLI mode | Decided | CLI mode enables only Claude Code's WebSearch and WebFetch, never shell or file tools (B8). API and OpenRouter mode use the bot's own tools (W1). Switch: `WEB_TOOLS`. |
| E2 | Who may use the web | Decided | Everyone who can trigger the bot can make it search and read links (W1). Groups are already limited by B15. |
| F1 | Quoted replies | Decided | When a message replies to another, the quoted sender (resolved by WhatsApp ID) and text are added as `(replying to NAME: "…")`, cut to 300 characters in stored history and 4000 in the request. A trigger replying to an image sends that image. |
| F2 | History before joining | Decided | Not possible: WhatsApp only delivers group messages from when the bot joins, end-to-end encrypted. To ask about older ones, reply to them (F1). |
| F3 | A quote is part of the request | Decided | When a trigger replies to a message, the quoted message is always part of the request, whether the sender added words or only tagged the bot. The sender's words (if any) say what they want about it; a bare tag asks for a response to the quoted message; the requester is the sender, not the quoted writer. |
| F4 | An unquoted DM answers the last bot message | Decided | In a DM, a trigger that quotes nothing and comes right after a bot message is sent as replying to that message (`(replying to <BOT_NAME>: "…")`, as F1/F3), so a bare "ye" answers the bot's last question, not an older item from the summary or memories. Only the request gets the quote; the stored line doesn't. Groups are unchanged. |
| F5 | A recent group photo comes with a bare tag | Decided | In a group, a trigger that quotes nothing gets the photo posted in that chat in the last 5 minutes, downloaded only then; the request says whose photo it is and how old (`image="attached: the photo NAME posted N minutes ago"`). The last photo per group is kept in memory only, never on disk. A quoted message (F1) always wins. |
| F6 | "That" in a group | Decided | System-prompt rule: in a group, a trigger that quotes nothing and says "that", "this" or "it" means the newest transcript line it can refer to, usually the requester's own message(s) just before it or the line right above, never an older answer of the agent's unless that is the line right above. "Revise that" about the requester's own line rewrites their text in their voice. If it is genuinely unclear, the agent asks in one short line. Prompt only, no hidden quote in code (unlike F4), since the right line isn't always the requester's. Golden cases: own lines just before, and the agent's answer right above. |
| G1 | Model providers | Decided | Three providers: `anthropic` (A5), `openrouter` (`OPENROUTER_API_KEY`) and `openai` (G5). `DEFAULT_PROVIDER` picks one at startup (default `anthropic`); `!provider` switches (L13). Each has its own model key (L13) and its own reasoning effort (Y1). |
| G2 | OpenRouter client | Decided | Plain `net/http` against OpenAI-style chat completions; no new dependency. Tools run in a client loop, as in the Claude API client. Effort maps to reasoning effort, with reasoning excluded from the reply. |
| G4 | Images on OpenRouter | Decided | Send the image. If it is rejected (400/404, e.g. no image input), retry once without it and tell the model to say it couldn't see the image. |
| G5 | OpenAI-compatible provider | Decided | Provider `openai` points the OpenRouter client (G2) at any OpenAI-compatible chat completions API: `LLM_BASE_URL` (API root), `LLM_API_KEY` and `LLM_MODEL` (required, no default). It sends `reasoning_effort` (the provider's Y1 effort) and none of OpenRouter's routing (P2, P3) or headers. Tools and the image fallback (G4) work as on OpenRouter. Embeddings (J2) still use `OPENROUTER_API_KEY`. |
| H1 | Knowledge curator | Decided | A background pass reads new messages in every chat the bot sees (groups it is in, whitelisted DMs), including ones not addressed to it, and saves facts with the J3 tools (tier `inferred`). A pass runs per 16 unread messages in a chat, or after 10 minutes of quiet if any are unread, before the messages leave the window. Passes run one at a time, without web tools, on the active provider. Group members are not told (B11). |
| H2 | What the curator records | Decided | Durable facts about participants and people they mention: identity, relations, studies/job, origin, interests, habits, opinions, plans, running jokes, how they treat the bot. Compressed English facts, no duplicates of known facts. Never sensitive data (passwords, phone numbers, addresses, health, money). Todos are skipped (U1). |
| H3 | Nicknames and merging | Decided | Nicknames are saved as `Alias: <name>` facts, and name lookups match aliases. When an alias matches a name-only profile (D4), its facts move to the real person and the name-only profile is deleted. |
| I1 | API tools | Decided | Client-side tools in the same loop as `search_facts` on every tool-capable provider: a generic `http_request` (any method, headers, body; `find` to grep big responses, `offset` to page; 20k characters per result), and the tools of configured MCP servers, named `mcp__<server>__<tool>`. The model looks for an app's API docs instead of guessing endpoints, and calls the API when a web page needs JavaScript. When the 8 tool rounds run out, one final call without tools forces an answer, and leaked tool-call markup is stripped. Switch: `API_TOOLS`. |
| I2 | Who may use API tools | Decided | `http_request`: anyone who can trigger the bot. MCP tools: whitelisted requesters only. `http_request` reaches public addresses only: loopback, private, link-local (cloud metadata), CGNAT and multicast IPs are refused at connect time, also after redirects and DNS tricks; proxies are off. Accepted trade-off: group members can make the VPS request public sites. Tool results are data; the model must not repeat secrets from them. |
| I3 | MCP configuration | Decided | Only the owner configures MCP servers, in `mcp.json` (Claude Desktop format: `command`/`args`/`env` for stdio, `url`/`headers` for streamable HTTP) at `MCP_CONFIG` (default `DATA_DIR/mcp.json`, secret like `data/`). Servers connect at startup (restart after editing); a failing server is logged and skipped; a dead session reconnects once. Uses the official MCP Go SDK. |
| I4 | Stored API keys | Decided | Owners keep API credentials in `DATA_DIR/api_keys.json` (secret, chmod 600): a map of host to request headers, e.g. `{"tasks.example.com": {"Authorization": "Bearer <token>"}}`. `http_request` adds them only for whitelisted requesters and only on https requests to that exact host; a redirect that leaves the host or https drops them. The model never sees a key: the tool description lists only hosts, and a key echoed back is replaced with `[stored credential]`. Edited with `!key` (L1). Accepted risk: an owner's request can make the model use a key for any method on its host, writes included. |
| I5 | Google Workspace MCP | Decided | Dropped (Z): the Google Workspace MCP server is removed from `mcp.json`. Its 72 tool definitions went into every owner prompt (about 10k tokens) and were called 3 times in a week of about 1,200 replies. The generic MCP support (I1-I3) stays, so a server can be added again. Earlier design: a dedicated Google account with OAuth, the third-party stdio server `sputnicyoji/google-workspace-mcp-with-script`, all Docs/Drive/Sheets/Gmail/Calendar/Apps Script scopes. |
| I6 | Own Google bridge via Apps Script | Decided | Dropped (Z): moot once I5 was dropped; a new Question if Google access is wanted again. Earlier proposal: Avoid I5's OAuth consent-screen setup with an Apps Script web app owned by the agent's account (execute as the agent, access: anyone, guarded by a long random secret). The agent's account approves it once; the grant doesn't expire weekly. One `doPost` runs ops with DocumentApp, SpreadsheetApp, DriveApp, GmailApp and CalendarApp. The wagoya side is a stdio MCP server in the same binary (`wagoya google-mcp`, existing MCP SDK) in `mcp.json`, so I2 keeps it to whitelisted requesters; about 15 tools (docs, sheets, drive, gmail, calendar). Secret and URL live in `data/`. Limits: Apps Script quotas (about 100 Gmail sends per day, 6 minutes per call), 1-3 s per call, a public URL guarded only by the secret. Open: the tool list; Apps Script code in this repo (`gas/`) pasted by hand or pushed with `clasp`; cleanup of I5 once replaced. |
| J1 | Fact validity | Decided | Each fact has `valid_from`, `invalid_at`, `invalid_reason`, `said_by` (person key), `chat`, `tier` (J4) and `kind`: `fact`, `state` (short-lived, expires after 24 h), `claim` or `joke` (unverified talk). Outdated or contradicted facts are invalidated, not deleted, and kept as history; search returns only valid facts unless history is asked for. Facts from before this have tier `legacy`, with `Claim:`/`Joke:`/`Behavior:` labels mapped to `kind`. |
| J2 | Hybrid retrieval | Decided | FTS5 search, scoped to a named person and ranked by the rest of the query, plus embedding search via OpenRouter (`EMBED_MODEL`, default `openai/text-embedding-3-small` at 512 dims; empty disables; none on the Anthropic provider). Results are the union of the embedding hits close to the best one and the FTS hits, ordered valid first, by tier (J4), then relevance. The embedding call runs in parallel with FTS, query vectors are cached, and search falls back to FTS if embedding fails. Vectors are stored per fact as BLOBs (brute-force cosine; no sqlite-vec, C4) and dropped when a fact is deleted or reworded; a background loop embeds facts without one. Free embedding endpoints are not used: they may log or train on inputs. |
| J3 | Tool-based memory writes | Decided | Memory is written through tools: `save_fact(subject, content, kind, source)`, `invalidate_fact(id, reason)` and `save_memory(category, content)`. The bot validates input, attaches provenance (J1, J4) and returns errors to the model. The curator uses the same tools. `<persona>` stays a tag (D2). CLI mode has no custom tools, so hidden tags stay its fallback. |
| J4 | Source tiers | Decided | Tiers, highest first: `owner` (a whitelisted person said it), `self` (the person about themselves; a claimed self statement must come from someone who spoke in the prompt), `participant` (someone else in the chat), `inferred` (curator). Search ranks by tier and labels anything below `self` as unverified; a lower tier can't invalidate a higher one; claims about another person's identity are always `claim`. Anyone can still add facts (D4); the tier decides weight. |
| J5 | Token accounting | Decided | The bytes-per-token ratio is learned per model from the first round's reported prompt tokens (a running average, stored in `settings`, starting at 3, with a 10% safety margin); tool definitions count in the fixed part. Caps: each history line at most 2,000 characters, the request at most 16,000. Trim order: history, then memories beyond the top 3, then summary, then people other than the requester, then the last memories, then the request. |
| J6 | Eval harness | Decided | A golden set runs on a cheap model before every deploy: trigger vs no trigger, reply to an image, prompt injection, persona change by a non-owner, cross-chat "what do you know about X", invalidate, contradiction handling, tier ranking, no tool markup or narration in replies, plus the guard cases from K and S rows. Each case has a checkable expectation; the deploy stops on failures, with a flag to skip. Budget $0.05 per run. Cases run 6 at a time, each on its own store. |
| J7 | Scheduler | Decided | A `schedule_message` tool; jobs are stored in SQLite, sent through the pacer (B18) and survive restarts. Listed and cancelled with `list_scheduled` / `cancel_scheduled`. Details in J9, J10 and T1. |
| J8 | Rolling chat summary | Decided | Each curator pass (H1) rewrites a per-chat summary (at most ~300 words) from the old summary plus the new messages. It is shown before the transcript. |
| J9 | Recurring and self-initiated jobs | Decided | Recurring jobs are allowed ("every day at 12"), and the model may schedule on its own initiative (e.g. a meal or sleep nag), not only on request. Limits in J10. |
| J10 | Scheduler limits | Decided | Whitelisted requesters can schedule one-off or recurring messages in any chat they are in (by group name, or their own DM); others only one-off reminders for themselves in the current chat. Self-initiated jobs only in chats with a whitelisted member. At most 10 pending jobs per chat; recurring at most hourly (hourly, daily, weekdays, weekly). People cancel their own jobs, owners any, self-initiated included. A one-off missed while the bot was down is sent if under 12 h late, else dropped; a recurring one skips missed runs. |
| J11 | Repetitive facts overwrite | Decided | A new fact that nearly repeats a stored valid fact of the same person overwrites it in place, and the old copies are deleted, not kept as history. Near-duplicate: same label, at least 2 shared content words and at least half the content words of the shorter fact (stopwords, generic verbs like asks/says/calls, and short words ignored; plural s trimmed). `Alias:` facts are never merged. A less trusted source can't overwrite a more trusted fact (J4): the new one is dropped. No cap per label. |
| J12 | Merge profiles of the same person | Decided | (1) By LID/number: when a person's LID and number are both known, a `pn:<number>` profile merges into the LID profile. Two LID profiles are never merged. (2) Guessed from chat: a `name:` profile merges into a real account when its name or a nickname matches (a word equal to, or the start of, a word of the other, at least 3 letters) and that account is in a chat the facts came from; exactly one account must qualify. A `name:` profile with no facts merges on a single name match. The old name is kept as an `Alias:` fact. Runs at startup and after a curator pass that saved something. Facts move with their tiers and history. |
| K1 | Standing preferences in every prompt | Decided | The requester's owner-tier `Prefers:`/`Rule:` facts always go into `<people>`, an exception to D7's counts-only rule, so a standing rule applies without a search. Z9: preferences rank as style, below the persona and the hard rules. |
| K2 | Grounding claims about the past | Decided | System-prompt rule: claim what someone (the bot included) said earlier only if it is in the transcript, summary or a tool result. When told it said something it didn't, the bot finds the line where it happened instead of defending it. |
| K4 | Current states in every prompt | Decided | In tool mode, the requester and everyone who spoke in the window are listed with their newest 3 valid `state` facts (Z2: group members listed only by L5 get none) (any chat, newest first, with "since"). A newer state beats older ones, the summary and this chat's transcript. Another exception to D7. |
| K5 | People are never merged | Decided | Every person is their own WhatsApp account: nothing may treat or record two people as the same person, interchangeable, or one's alt, even as a joke or a claim. Enforced in code: the store drops such facts and memories, `save_fact` and `save_memory` reject them with a reason, and the summary loses such sentences. The prompts also say a transcript line's speaker is the name before the colon, while a nickname inside the text is who is addressed. Folding a name-only profile into the account it names (H3, J12) isn't a merge of two people: it is one account. |
| K6 | No handles in kept text | Decided | Handles are per prompt, so kept text names people only by name. The curator prompt says so and shows the forbidden forms ("Jim (P2)", "Jim [P2]", "P2"); the server strips any handle left in a summary or `save_memory` text (mapped to the name it stood for, else "someone"). |
| K7 | Addressee labels | Decided | A transcript line gets ` to="…"` only when the server knows who it is for: every DM line is to the bot ("you"); a reply goes to the quoted writer; @mentions go to the tagged people; the bot's replies go to the requester plus anyone it tags. No signal, no label, never a guess. Stored as `to_bot`/`to_names` on `messages`. |
| K8 | Pronouns belong to their writer | Decided | "I/me/my" are a message's writer and "you/your" its addressee; the bot switches to its own point of view when echoing someone ("my PA" from the owner becomes "your PA") and never swaps who holds a stated role. A nickname someone uses for the bot is about the bot, and it never calls them by it. Golden cases are guards. |
| L1 | `!key` | Decided | An owner, in a DM, sends `!key <host or URL> <token>` (saved as `Authorization: Bearer <token>`), `!key <host> <Header-Name>: <value>`, `!key <host> remove`, or `!key` to list hosts. Handled before the model: never stored, curated or sent to a provider. The key goes to `api_keys.json` (I4, written atomically, mode 600) and works at once. Replies never echo the secret and ask the owner to delete their message. In a group it is refused with a warning to revoke the token. |
| L2 | `!reset` | Decided | An owner sends `!reset` (in a group, also as "@bot !reset"). The curator first reads unread messages so no facts are lost, then the chat's transcript and summary (J8) are deleted. Facts, memories and jobs stay. The command and reply are not stored. |
| L3 | Tagging people | Decided | The model tags with "@P2" (a handle from `<people>`; "@Full Name" also works). The bot sends a real mention (`MentionedJID`: LID, or number for `pn:` profiles) and stores "@Name" in history. In a group, a reply's "@<digits>" that is a current member's LID or phone number is a real mention too; other digits stay plain text. The prompt's `<chat>` line says group chat or private DM. Scheduled messages tag too (L10). |
